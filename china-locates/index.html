Architecture DecisionsEngineering trade-offs

The design separates state construction from request serving so that freshness, consistency and throughput can be reasoned about independently. Each choice makes one property stronger while keeping its cost explicit — the architecture is the result of these trade-offs, not just a diagram of components.

01

Kafka for coordination

Kafka carries the high-volume event stream and request/response flow, decoupling producers from consumers and allowing the platform to absorb bursts without coupling every service directly.

02

Redis for the hot state

Redis keeps the reconciled inventory close to the readers. Targeted lookups avoid repeated full-table scans and help move reconciliation and short-sell endpoints from roughly 30 seconds to sub-second responses.

03

Single writer, multiple readers

One writer owns reconciliation and produces a coherent inventory snapshot; stateless readers scale horizontally behind it. The trade-off is deliberate: centralise mutation to make consistency easier to verify, then scale the read path independently.

04

Consistency through shared state

Five readers do not maintain independent copies of inventory. They read the same Redis-backed snapshot and are admitted only while the writer heartbeat proves that the state is current enough to serve.

05

Failure is a safe outcome

If a reader loses its connection or the writer stops renewing its heartbeat, that reader stops serving rather than guessing. Recovery is explicit: restore health, rebuild state if needed, then reopen the read path.

When dependencies degradeReliability by design

For a trading workflow, an uncertain answer is worse than a visible refusal. The platform makes freshness and dependency health part of the request path.

FAIL-CLOSED

Stale state is not served

Heartbeat-gated readers refuse requests when the writer or shared state is no longer demonstrably healthy, preventing a degraded snapshot from being presented as a current allocation decision.

RECOVERY

Rebuild from the event flow

Separating ingestion, reconciliation and serving gives the system a clear recovery path: restore the writer, rebuild the shared snapshot, then reopen readers once health checks pass.

OPERATIONS

Health is visible

Prometheus instrumentation covers more than liveness: around 15 operational metrics help track freshness, throughput and request behaviour during triage and recovery.

Production lessons learnedWhen readers ran out of memory

An OOMKill on the reader pods became a useful example of production engineering: start with the user-visible symptom, follow the evidence, fix the resource behaviour and make the regression harder to repeat.

01 · SYMPTOMS

Readers disappeared under load

Reader pods were being OOMKilled, reducing the available serving capacity and creating an operational signal that could not be treated as a simple availability blip.

02 · DIAGNOSIS

Follow memory, traffic and payloads

Correlating pod memory, request volume and the shape of the data handled by the readers narrowed the issue to memory growth in the serving path rather than Kafka or Redis availability.

03 · CORRECTION

Reduce the working set

The reader path was changed to avoid retaining unnecessary data and to keep lookups targeted, reducing peak memory pressure while preserving the shared-state model.

04 · PREVENTION

Make the limit observable

Resource behaviour became part of the operational picture: monitor memory alongside latency and throughput, keep health gates meaningful and use the metrics to catch a regression before Kubernetes has to kill a pod.

Why traders feel the differenceBusiness impact

The outcome is not just a faster backend. It is a more dependable way for front-office users to turn live inventory into an actionable locate decision.

01

Faster decisions

Endpoints that once took roughly 30 seconds now return in under a second, reducing friction in time-sensitive locate and short-sell workflows.

02

One shared answer

Readers work from the same reconciled snapshot, so traders get consistent inventory decisions rather than pod-dependent results.

03

Built for the real workload

The platform handles around 700 million updates and 10,000 locate requests per day across an inventory of roughly 280,000 records.
